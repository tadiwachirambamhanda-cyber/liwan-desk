# Plan: Memory (Step 2 of 4)

## Goal
After this, the agent remembers every conversation: each message in and out, each step the agent took (with its cost) and each hand-over is saved in the Supabase database. Reloading the phone page brings the whole chat and the "What the agent did" panel back, the agent knows whether a person has taken over a conversation, and its replies take the last few messages into account.

## Feature
- No feature ID (the project has no feature list yet). This is Step 2 of the four steps: database, memory, staff inbox, real WhatsApp.
- Done check: send "hi", then "I want prices" on `/phone`, reload the page: both messages, both replies and the panel steps come back exactly as they were, and the database holds them.

## Steps
1. **Connect the app to the database.** Install `@supabase/supabase-js`. Add `src/lib/db.ts`: a server-only client that reads `SUPABASE_URL` and `SUPABASE_SECRET_KEY` (never `NEXT_PUBLIC_`). Run the app's functions in the Mumbai region, next to the database, so each database call takes a few milliseconds instead of about 200. Done when a throwaway script reads the 10 weekly free times through `db.ts`, and `npm run build` passes with no environment variables set.
2. **Write the memory code, `src/lib/memory.ts`** (the only file that talks to the tables): find or create a conversation, save a customer message (ignoring a WhatsApp message id it has already seen), read the conversation's status and its last 6 messages, save a whole run (the reply, the steps, the Jev / rules / Claude panel details with cost and tokens, and any hand-over), and rebuild a conversation for the panel. Done when a script saves a made-up conversation, reads it back identical, and deletes it.
3. **Use it in `/api/whatsapp`, in this order.** (a) The existing checks (size, signature, rate limit). (b) Find or create the conversation in one safe step (an upsert on source + external id, so two messages arriving together cannot create two conversations). A request with no WhatsApp signature is the simulator, a signed one is WhatsApp; this is stored as the conversation's source. (c) Save the customer's message first, so a crash never loses their words. A WhatsApp message id the database has already seen stops the run here, so a retry costs nothing and gets no second reply. (d) Read the conversation's status and its last 6 messages. (e) Run the agent as today. (f) Save the results (the reply, the steps with costs, any hand-over and the conversation's status) together in one database function, so a half-saved run cannot happen and a hand-over always sets the status to `with_person` in the same step. If the database cannot be reached, the customer gets the holding reply and a log line is written (nothing else can record it yet); see Questions and "What could break". Done when "hi" on `/phone` leaves one conversation, two messages (in and out) and the steps with costs in the database.
   - **While a person has the conversation (`with_person`):** the message is still saved and still sorted (Jev costs about $0.00003). Normally the agent stays quiet. If the message is an emergency, a new urgent hand-over is added and the sympathetic emergency reply is sent, so an emergency never sits unseen behind a receptionist who has stepped away.
4. **Give the agent memory in its words.** Claude's writer receives the last 6 customer and agent messages (oldest first, none if the conversation is new), in a clearly fenced block, so it does not greet again in every reply or repeat itself. Receptionist messages are not included. Code, not Claude, decides "second greeting": if the saved history already holds a welcome from the agent, a plain greeting gets a short fixed "Hello again" (English or Arabic) instead of the full welcome. Jev still sees only the current message. Done when "hi", "hi" shows the short second greeting (also in Arabic) and "hi", then "I want prices" gets a price reply that does not start with "Hello".
5. **Three small routes for the phone page**: read a conversation's history, save a receptionist's reply, hand the conversation back to the agent. "Hand back" sets the status to `bot` and resolves the open hand-overs in one database function. Conversations are found by a long random id (a UUID), the routes only work for simulator conversations (never WhatsApp ones), and only when `SIMULATOR_ENABLED=true` (or in development). Done when each returns the right data with the switch on and is refused with it off.
6. **Update the phone page.** The page keeps a random session id in the browser, restores the chat, the panel and the handed-over list from the database on load (and shows a clear "could not load the history" message instead of an empty chat if that fails), and has a "New chat" button to start fresh. The receptionist reply and "hand back" buttons call the routes. The "with a person" pause comes from the database instead of the old header. Done when reloading keeps everything, including an open hand-over and its replies.
7. **Check everything.** First in code, then on a Vercel preview after you add the two Supabase keys there (I guide you through it).

## Files

- Change: `src/app/api/whatsapp/route.ts`, `src/lib/reply.ts`, `src/app/phone/page.tsx`, `package.json` and its lockfile.
- The tables from Step 1 are not changed. The one new migration adds two database functions, "save a run" and "hand back", each doing its several writes together. They are locked like the tables: only the server key can run them.

## AI parts
- **Claude (the writer, `claude-sonnet-5-5`)** gets the last 6 messages of the conversation as context, inside its own labelled block, so the intro and closing line fit the conversation. Everything else is unchanged: code still builds every list, price and time, and every reply still passes the same checks (prices, times, discounts, medical advice, false claims, links) before it is sent.
- **Jev** still sees only the current message. More context could change its answers in ways I cannot predict.
- **Rules stay in code.** Whether a conversation is with a person comes from the database, not from the model.
- Earlier messages are customer words and are treated as data, never as instructions.
- If Claude's output fails the checks, nothing changes: a person answers.
- Expected cost: no new calls. About 200 more input tokens per Claude call, roughly $0.0004 more per reply.

## Sending and data
- Nothing new leaves the app. Messages, replies, steps and hand-overs are now stored in the Supabase project `liwan-desk` (Mumbai). Today the data is made up. Later it will hold phone numbers and real messages.
- The tables stay locked: only the app's server key can reach them, and that key never reaches the browser. The new routes are closed unless `SIMULATOR_ENABLED=true`, find conversations only by a long random id, and never serve WhatsApp conversations. **`SIMULATOR_ENABLED` must be off on any deployment that holds real patient data**, and the staff inbox (Step 3) adds real staff access.
- **A gap that must be fixed before real WhatsApp (Step 4):** if the database is down, the holding reply goes out but nothing can record the message, so it would be lost. For the simulator that is harmless. Before real WhatsApp the webhook must answer with an error so WhatsApp retries (checked against WhatsApp's retry rules then), or raise an alert.
- Secrets needed, server side only: `SUPABASE_URL`, `SUPABASE_SECRET_KEY` (already in `.env.example` and your `.env.local`; you add them to Vercel).
- Logs: only counts, ids and timings, never message text or phone numbers.
- Replies still go out on their own only after every code check passes. Emergencies, complaints, cancellations, requests for a person, unlisted prices and anything unclear still go to a person.

## What could break
The riskiest step is 3: every reply now depends on the database, so a slow or failing database could slow or stop answers. That is why the function runs next to it in Mumbai and why a database failure hands over safely instead of crashing. It could also change the pause behaviour that works today (the page used to send a header), so the hand-over checks are repeated before and after.

## Not doing
- The staff inbox (Step 3) and real WhatsApp sending (Step 4).
- A login for the phone page routes (Vercel's login protects the preview; the staff inbox adds real staff access).
- Booking: the agent still only offers times and never saves an appointment. Patients are not linked to conversations yet.
- Deleting old messages or retention rules (needed before real patients).
- Summaries of long conversations: only the last 6 messages are remembered.
- Live updates (the page reads history on load, not as it happens).
- A shared rate limit. It stays in each server's memory, so on Vercel several instances each count on their own. A shared limit comes later.
- Recovering a chat after the browser's saved session id is cleared: that conversation is then no longer reachable from the page, but it stays in the database.

## Questions
1. **If the database cannot be reached**, should the agent hand the message to a person (my default, the safe choice), or still answer without memory?
2. **How much memory?** I would remember the last 6 messages. More costs a little more per reply.
3. **Keep every message forever** for now, since it is all made up? I would, and add deleting rules before real patients.
4. **An emergency while a person holds the conversation:** I would still send the sympathetic emergency reply and add an urgent hand-over, even though the agent is otherwise quiet. Is that right?

## Plan check
A fresh reviewer read this plan with no explanation. Seven findings, all checked:
1. Anyone with a shared preview link could read simulator chats (MAJOR): **fixed.** Conversations are found only by a long random id, simulator conversations only, and the plan states that the simulator switch must be off with real data.
2. Database down means a "hand-over" that nothing records (MAJOR): **fixed.** The plan now says this path only logs for now and names the fix needed before real WhatsApp (an error answer so WhatsApp retries, or an alert).
3. Order of saving, duplicates and two messages at once (MAJOR): **fixed.** Step 3 now gives the exact order: upsert the conversation, save the customer message first (a duplicate id stops the run before any model call), read the history, run, save everything together.
4. An emergency while a person holds the conversation (MAJOR): **fixed.** The message is always saved and sorted; an emergency still gets an urgent hand-over and the emergency reply. Added to the checks and as question 4.
5. A half-saved run, and status drifting from hand-overs (MINOR): **fixed.** Two database functions ("save a run", "hand back") do their writes together. One new migration, locked like the tables.
6. "Hello again" and the history as an attack route (MINOR): **fixed.** Code decides the second greeting from the saved history; Claude gets only customer and agent messages in a fenced block; checks added for an injection attempt in the history and an Arabic greeting twice.
7. Smaller gaps (MINOR): **fixed:** `vercel.json` named and the region checked against Supabase's; the 6-message order and empty case stated; an error state when the history cannot load. **Noted, not changed:** the in-memory rate limit stays weak on Vercel (listed under "Not doing"), and a cleared browser id orphans the chat (also listed). **Dismissed:** the phone page's narrow-width layout, because this plan does not change the layout.

## Changes from the plan
- Added `src/lib/gate.ts` (the one place that decides whether the phone page's routes are open, and their shared 404 and 503 answers).
- With no database configured the agent now runs without memory in development and shows a "Memory is off" step. On a hosted deployment a missing database counts as a failure, like an unreachable one: the customer gets the holding reply.
- The phone page reads its session id with React's `useSyncExternalStore`, because the project's lint rules do not allow setting state straight from an effect (the rule stayed on).
- The history route returns an empty chat for a new session id rather than an error.
- The old test scripts were lost when the temporary folder was cleaned, so one compact regression script was rewritten (64 checks).
